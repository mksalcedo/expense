# Amazon "Needs Review" Fixes: Parser Multi-Order Bug + Review Queue Streamlining

Status: **built and verified against real production data**. Written so an interrupted/disconnected session can resume without re-deriving the design from conversation history.

**Verification note**: after deploying, triggering a real Amazon sync re-scanned the exact digest email described below (its incremental window happened to include it again) - confirmed via direct `psql` query that the previously-silently-dropped two orders (`113-5634569-7569032`, `113-6275981-3164251`) were correctly added as `NeedsReview` placeholders this time, each with its own correct `NeedsReviewReason` ("Bundled with 2 other order(s) in one digest email"), `SourceMessageId`, and per-order `OrderDetailsUrl` - while the third order in the same digest (`113-6641743-8180261`, already captured earlier under its real item title) was correctly left untouched, not duplicated. The Review Queue's "Why is this flagged?" toggle was confirmed to render the real captured reason and full raw email body for these rows in the live app.

## Problem

Reviewing a real `NeedsReview` Amazon order in Review Queue surfaced three usability gaps (can't edit item text without leaving for Transactions, can't split a placeholder into the real multiple items, can't see the source email) and, while verifying a proposed fix against real Gmail data, a fourth and more serious **parser correctness bug**: a live digest-style email bundling 3 separate orders in one message causes 2 of the 3 to be silently dropped (no placeholder, no `SyncIssue`, no trace at all) - `AmazonOrderEmailParser` was built assuming exactly one order per email everywhere, which was never true. Both dropped orders happened to be $0.00 today, so there's no financial impact yet, but a future digest with real dollar amounts would silently under-count spending.

This plan covers: (1) fixing the parser to handle multiple orders per email, (2) capturing enough context (raw body, source message id, a real "view this order" link, a reason) on every `NeedsReview` placeholder so investigating one never requires leaving the app or re-finding the email in Gmail, and (3) surfacing that in Review Queue with an inline edit (reusing an already-existing backend method) and a real Amazon deep link.

**Process: TDD throughout, as with every part of this app.** For each part below: write the failing test first (using real-shaped fixtures where noted, not synthetic ones), confirm it actually fails, then implement until it's green - not implement-then-test. Run the full `dotnet test` suite after each part, not just once at the end.

**Financial impact, traced through the real code before deciding to proceed (not assumed):** a missed Amazon order does **not** affect the Forecast - `ForecastEngine`/`AmexCycleCalculator` sum every real Amex `BankTransaction` unconditionally (`src/Expense.Domain/Services/Forecast/ForecastEngine.cs`, the `chargeTransactions` query has no `IsAmazonMerchant` or `CategoryId` filter at all), so the balance/Amex-payment-due math is always correct regardless of whether the Amazon email parsed. It **does** affect the Spending Tracker: `SpendingTrackerService.cs` explicitly filters `!t.IsAmazonMerchant` out of both its per-category `Actual` and `PendingAmount` queries, relying entirely on `AmazonOrderItem` for Amazon spend - so a silently-dropped order has zero representation anywhere on that page (not even as "Pending"), even though the real bank charge sits correctly in the DB. Sampled ~30 real order emails (~7.5 weeks, June-July 2026): exactly one true multi-order bundling incident found (the one below), and the two silently-dropped orders in it were both $0.00 - so the known dollar impact to date is zero, though the gap is real and would matter the next time a bundled digest contains a nonzero amount.

**Explicitly deferred, not in this plan**: a fourth idea discussed - reusing the Amex screenshot/Claude-vision pipeline against Amazon's own order-detail page as a standing fallback for whatever the parser still can't handle. That's a materially larger, separate feature (new prompt, new review/confirm UI, replacing placeholder rows with real ones). Recommendation: build it as a follow-on once the raw-body/reason capture below has accumulated enough real examples to design its prompt well.

## Real evidence gathered (not guessed)

- Real order `113-4355508-6173055` ($51.40, the one that prompted this) confirmed via direct Gmail lookup: its confirmation email genuinely has zero item-level detail - only `Order #`, `Grand Total`, and a `View or edit order` link. The parser's placeholder fallback was the correct call for this one.
- That link's URL format is **not stable enough to construct from `OrderId` alone** - two different real path structures observed in emails from the same week: `https://www.amazon.com/gp/css/order-details?orderId=...&ref_=TE_simp_od` (existing test fixture) vs. `https://www.amazon.com/your-orders/order-details?orderID=...&ref_=p_btn_fed_veo` (real live email today). Amazon's plaintext MIME encoding also mangles the `=` character in query strings (almost certainly a quoted-printable `=3D` artifact) - the raw embedded URL text can't be trusted verbatim either.
- A real live email ("Ordered: 4 Nutrition & Wellness and Grocery items", 2026-07-21) bundles **3 separate orders** (`113-6641743-8180261` $16.08, `113-5634569-7569032` $0.00, `113-6275981-3164251` $0.00) in one message, each with only an `Order #`/`Grand Total` pair, no items. Checked the real database directly: only the first order was ever imported (as a real, non-placeholder row - it happened to already exist from a separate itemized confirmation email, so dedup silently absorbed it). The other two have **zero trace anywhere** - not a placeholder, not a `SyncIssue`.
- Traced the root cause in `AmazonOrderEmailParser.Parse` (`src/Expense.Domain/Services/Ingestion/Amazon/AmazonOrderEmailParser.cs`): `OrderIdPattern().Match(...)` and `GrandTotalPattern().Match(...)` are both first-match-only (`Regex.Match`, not `.Matches`), and `BuildPlaceholderOrder` always returns a single-element list. There is no loop anywhere in `AmazonGmailSyncService.RunAsync` → `AmazonImportService.ImportOrderAsync` → `AmazonOrderEmailParser.Parse` that iterates multiple orders within one message body.

## Part 1: Parser fix - handle multiple orders per email (TDD)

- In `AmazonOrderEmailParser.ParseItemizedOrder`, the existing `itemMatches.Count == 0` branch (the one that calls `BuildPlaceholderOrder`) is exactly where multi-order digests land. Change it to: find **all** `Order #` matches (promote `OrderIdPattern` usage here to `.Matches`, not `.Match`), and for each one, find its own nearest following `Grand Total` occurrence (bounded by the next `Order #` match's position, or end of string) - producing one placeholder per pair instead of only the first. When there's exactly one pair (today's normal case), behavior is unchanged - this is a strict generalization, not a rewrite, so the existing 300+ real-order-verified itemized-parsing path is untouched.
- Apply the same generalization to the "simplified"/inline path (`InlineOrderIdPattern`/`OrderTotalPattern`) for consistency, since it's the same class of bug and cheap to fix alongside - no direct evidence yet that this specific path bundles multiple orders, but no reason to leave the same latent bug in the sibling code path.
- Do **not** attempt to generalize the itemized-with-items path (`ItemPattern().Matches(...)` case) to multiple orders - no evidence today of a real email bundling multiple *itemized* orders in one message, and guessing at that structure without a real fixture would violate this project's "verify with hard evidence, don't guess" standard.
- **Write these tests first, confirm they fail against today's parser, then implement the fix.** New tests in the existing Amazon parser test file (`tests/Expense.Domain.Tests/Services/Ingestion/Amazon/` - confirm exact file during implementation), using a **real-shaped fixture** modeled directly on the actual digest email body captured during planning: assert `Parse` returns 3 placeholders (one per order id/total pair), each `NeedsReview = true`, correct `OrderId`/`Price` per order, and a regression test confirming the single-order case still returns exactly one placeholder unchanged.

## Part 2: Capture context on every `NeedsReview` placeholder (TDD)

Add four new nullable columns to `AmazonOrderItem` (`src/Expense.Domain/Entities/AmazonOrderItem.cs`) - only ever populated by `BuildPlaceholderOrder`, left `null` for normal itemized rows (no evidence those need it):

```csharp
public string? SourceMessageId { get; set; }
public string? RawEmailBody { get; set; }       // unbounded text, same as ImportRunProgressLine.Text
public string? NeedsReviewReason { get; set; }  // plain string, not an enum - reasons aren't fully known yet; this is the instrumentation that lets them emerge from real data over time
public string? OrderDetailsUrl { get; set; }
```

- `AmazonOrderEmailParser.Parse`/`BuildPlaceholderOrder` need a `messageId` parameter threaded through from `AmazonGmailSyncService.RunAsync` (which already has `message.Id` - it's just never forwarded past `ImportOrderAsync` today) → `AmazonImportService.ImportOrderAsync` → `Parse`. `ImportOrderAsync` itself needs no logic changes, since it already operates on the whole `AmazonOrderItem` object the parser hands back - just pass the id through.
- `BuildPlaceholderOrder` sets `NeedsReviewReason` to a short description of *why* (e.g. "No item detail in confirmation email" vs. "Bundled with N other orders in one digest email" for the Part 1 case) - this is the actual diagnostic value: once several months of real reasons accumulate, they can be reviewed to decide which recurring formats are worth a dedicated parser rule, rather than guessing.
- `OrderDetailsUrl`: detect which of the known link path templates (`your-orders/order-details` / `gp/css/order-details` - a small, explicit, extensible list) appears as a literal substring near this order's segment of the body, and construct the URL using that detected path **plus the already-reliably-parsed `OrderId`** (not the corrupted embedded query string) - e.g. `https://www.amazon.com/gp/css/order-details?orderId={OrderId}`. This avoids both failure modes: guessing a path we have no evidence for, and trusting a query string Amazon's own encoding mangles. Verify the constructed URL actually resolves against a couple of real orders during implementation before relying on it. If no known path template is found in the body, leave `OrderDetailsUrl` null (Review Queue falls back to a generic orders-history link in that case, not a broken deep link).
- New migration (`dotnet ef migrations add AddNeedsReviewContextToAmazonOrderItem --project src/Expense.Domain --startup-project src/Expense.Domain`), applied to both `expense_test` (automatic via `DatabaseFixture`) and the real production DB (`dotnet ef database update ... --connection "<prod connection string>"`, same pattern used for the earlier `AddImportRunProgressLines` migration).
- **Write the round-trip entity test first** (mirrors `tests/Expense.Domain.Tests/Entities/ImportRunTests.cs`'s style), confirm it fails to compile against today's entity, then add the columns/migration until it's green - same order as every other schema addition in this app.

## Part 3: Surface it in Review Queue (TDD)

- `PendingAmazonItemGroup` (`src/Expense.Domain/Services/Categorization/PendingAmazonItemGroup.cs`) gains `NeedsReviewReason`, `RawEmailBody`, `OrderDetailsUrl` (all `string?`) - threaded through in `CategorizationService.GetPendingAmazonItemGroupsAsync`'s `needsReviewGroups` projection. The underlying `AmazonOrderItem` fetch (`GetPendingAmazonOrderItemsAsync`) already pulls the full entity with no `.Select()` projection, so these fields are already available with zero additional query cost - only the `PendingAmazonItemGroup` construction needs updating.
- `ReviewQueue.razor` Amazon Items table (`src/Expense.Web/Components/Pages/ReviewQueue.razor`, lines ~123-172):
  - Add a "View on Amazon" link using `group.OrderDetailsUrl` when set, falling back to a plain link to `https://www.amazon.com/gp/css/order-history` (the general orders list, always reliable) when it's null - so there's always some actionable link, never a broken deep link.
  - Replace the current plain-text `@group.ItemTitle`/total display (for `NeedsReview` rows only) with inline `<input>` editors, reusing the existing, already-built `TransactionManagementService.UpdateAmazonItemDetailsAsync(itemId, title, price, quantity)` - add a thin delegating method to `IReviewQueueProvider`/`ReviewQueueProvider` so Review Queue doesn't need to depend on the Transactions page's own provider.
  - Add a collapsible "Why is this flagged?" toggle per `NeedsReview` row showing `NeedsReviewReason` and `RawEmailBody` (in a `<pre>`, matching the existing raw-body display pattern already used on the Sync Now page for `SyncIssue.Body`) - collapsed by default so it doesn't clutter the common case of a quick, confident manual fix.
- **Write these bUnit tests first, confirm each fails against the current markup, then implement.** New tests in `tests/Expense.Web.Tests/Pages/ReviewQueueTests.cs` (confirm exact file name during implementation): the View-on-Amazon link renders with the right href (and the fallback when null), the inline edit inputs call through to the new provider method, and the reason/raw-body section toggles open/closed and shows the right content.
